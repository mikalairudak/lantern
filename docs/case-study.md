# Lantern: a case study

Lantern plans a day in a city. A visitor types a sentence, "a slow Sunday in Lisbon with my partner", and a model writes the day as typed JSON. Deterministic components draw it as it streams in, and the visitor reshapes it on the client: dragging an energy curve swaps stops for quieter or livelier versions, a stop's version can be picked by hand, and the time axis shows when the light turns golden, then dark. It runs at [lanternday.com](https://www.lanternday.com). The [README](../README.md#architecture) describes how the pieces connect. This page covers why they are built that way, what each choice cost, and what the numbers say.

## The brief

- **A product a stranger can use in a minute.** A visitor arrives from a shared link and gives it 30 seconds to 3 minutes, so a few interactions had to be finished to the last frame, with everything else kept small ([roadmap](roadmap.md)).
- **One developer, working with coding agents.** I set the scope, the cut order and every product call; parallel Claude Code sessions, each in its own git worktree, took the roles of engineering lead, product designer, evaluation, security, SEO and ops. Lint enforces the design tokens, a pre-commit gate runs every check, and a fresh agent reviews UI work before it merges.
- **A fixed date.** The plan was agreed on 2026-10-20, with the send-out fixed for 2026-11-19. If the work falls behind, scope is cut in an order written down on day one, and the date holds ([roadmap](roadmap.md#if-we-fall-behind)).
- **No way to run up a bill.** Production's model workspace has a $100 monthly spend limit, and the app's own caps sit below it: $10 a day and $95 a month. The model's credits are prepaid, with no card on file, so when they run out requests stop rather than bill. The place lookups run on a free plan that needs no card.
- **Fixtures first.** Until 2026-10-27 the whole product ran on hand-made days, with no keys and no services. Live generation went to production on 2026-10-31.

## The decisions that shaped it

**The schema is the contract.** The model writes to a generation schema, and components read an app schema. A normalizer builds one from the other ([two layers](decisions.md#2026-10-20--two-layer-data-contract)). The generation schema uses no numeric, length or pattern keywords, so any provider's structured outputs can take it ([portable](decisions.md#2026-10-20--a-provider-portable-generation-schema)). The cost showed up live: one nullable field, added to a place and to its options, took the schema from 9 union types to 11, and the provider refused all 24 calls of a round because the compiled grammar was too large. Nullable is now spent sparingly, and a probe asks the provider before every round whether the schema compiles ([union types](decisions.md#2026-10-30--the-models-schema-keeps-its-union-types-few)).

**A day paints top to bottom and never jumps.** Fields are ordered the way they appear on screen, and the swap options stream last, after the timeline, so the first stop draws as soon as it is written ([field order](decisions.md#2026-10-20--field-order-is-render-order)). Every stream ends in one of seven named outcomes, and the simulator and the live route end alike, so the UI was designed against every ending before any model was called ([outcomes](decisions.md#2026-10-22--the-stream-reports-how-it-ended)). A cut inside the swaps still shows the day; a cut inside the stops gets a designed failure instead. Components are designed for every value the schema allows and every state of the stream, and each is laid out as a matrix in `/lab` ([Dynamic UI](decisions.md#2026-10-20--designing-for-dynamic-ui)). Frame-by-frame end-to-end specs also run on a page with its CPU slowed down. The cost is that swaps appear only after the timeline is complete.

**The normalizer repairs, refuses and reports.** A time written as "7:30", an overlap between stops, or an option too far to walk to is repaired. A day it cannot make whole is refused with a reason. Every repair is returned beside the itinerary, because the evaluation counts repairs and debugging starts from them ([normalizer](decisions.md#2026-10-22--the-normalizer-repairs-slips-and-refuses-what-it-cannot-make-whole)). Its latest rule drops a swap option that is already a stop in the same day.

**Cost protection holds the worst case before every call.** Before a day is written, the app reserves that call's worst case against its daily and monthly caps: $0.14 for a Sonnet day, from its input ceiling and its 12,000-token output cap. After the call it settles the real cost. A reservation that is never settled expires after ten minutes. A visitor's daily counts are keyed on a salted hash of their address, and the routes refuse to run if the database is down ([worst case](decisions.md#2026-10-28--every-model-call-holds-its-worst-case-against-the-spend-caps-before-it-is-made), [Postgres](decisions.md#2026-10-28--the-limits-and-the-log-live-in-postgres-and-every-hold-expires)). The day route writes a new city only when the intake has signed it, so it is not an open prompt endpoint ([signature](decisions.md#2026-10-30--a-day-for-a-city-lantern-has-not-written-carries-the-intakes-signature)). The first live pass showed why the app's caps are the real boundary: a $1.00 provider limit let $1.11 through.

**Checks, then an evaluation loop.** Quality is a set of pure functions over a request and a day: shape, banned phrases, script, walking radius, energy fit, day flow, light, the start, dinner and end words, the time each leg needs, and more ([checks](harness.md#eval-harness)). The same functions run on every fixture before each commit, on every live day the log keeps, and over golden sets of 12 day requests and 45 intake texts. One prompt change goes into each paid round, and stored outputs are scored again for free whenever a check changes. Five versions of the day prompt, `day-v4` to `day-v8`, measured on Sonnet; the rest, to `day-v11`, are in [the prompt versions](harness.md#the-prompt-versions):

| Version  | What changed                                    | What moved                                                             |
| -------- | ----------------------------------------------- | ---------------------------------------------------------------------- |
| `day-v4` | A meal is named by what is eaten there          | Meal names failed their rule in 47% of cases                           |
| `day-v5` | The meal-name rule moved into the prompt itself | 12%                                                                    |
| `day-v6` | Spelling became a rule of its own, with accents | Names written without their accents: 87% → 1%                          |
| `day-v7` | "Early start" defined as a first stop by 08:30  | 10 of 11 early days began at exactly 08:30                             |
| `day-v8` | "Around 07:30, no later than 08:30"             | Early days began at 07:30 to 08:00, one at 08:30; meal names 19% → 10% |

Each round of 12 days and their shadows costs about $1.10. By the round on `day-v8` the evaluation had cost about $10.

**Places are checked against open data, and meals are areas.** Each named place is looked up on Geoapify, which serves OpenStreetMap data and needs neither a card nor a map. A place is confirmed only when its distance, name and category all fit its kind ([Geoapify](decisions.md#2026-10-28--places-are-checked-through-geoapify-not-google-places)). The first live passes showed that every invented place, 29 of 408, was a café, restaurant or bar. So a meal now names a street or quarter and what is eaten there, and it is confirmed by how many places of its kind stand around it ([meals](decisions.md#2026-10-30--lantern-names-no-restaurant-café-or-bar)). The cost is that Lantern never recommends a restaurant.

**A changed word re-plans only what depends on it.** The model tags each stop with the request's words that shaped it. When the visitor changes "slow start" to "early start", only the morning window is written again, and the stops outside it stay exactly as they were. A merge cuts or drops what does not fit its window, and a check scores the re-plan as the model wrote it. The windows were measured on 36 recorded days first. A change that would touch more than two thirds of the stops re-plans the whole day instead ([contract](targeted-replan.md)). Dinner and company rewrite each run of the stops that name them; travel, and a company no stop names, change only the word, since three paid rounds showed their re-plans writing the same places again ([every word](harness.md#every-words-windows-travel-and-company)). The new part is a proposal: it is drawn on the same chart beside the day, and the visitor takes it or leaves it, so a re-plan that fails changes nothing, because nothing was changed ([the fork](decisions.md#2026-11-08--a-changed-word-proposes-its-part-beside-the-day-and-the-visitor-takes-it)). The route, the merge, its view and a golden set of six are built, and the server reads the kept stops from its own record of the day ([its own records](decisions.md#2026-11-02--a-re-plan-reads-its-day-from-the-servers-own-records)).

**Privacy by keeping little.** There are no accounts. A visitor's list of their days lives in their own browser. Product events carry a key that changes every UTC day ([events](decisions.md#2026-10-30--product-events-are-kept-under-a-visitor-key-that-lives-one-day)), what a visitor types is cleared from the log after 30 days, and one page states all of it ([what Lantern keeps](decisions.md#2026-10-30--what-lantern-keeps-is-said-on-one-page-and-what-a-visitor-types-is-cleared-after-30-days)). A day goes on being written after the visitor leaves, so a link to it still opens the whole day ([written to its end](decisions.md#2026-10-31--a-day-is-written-to-its-end-and-kept-to-be-opened-again)). Production showed this on 2026-10-31: a request cut after five seconds was read back a minute later with all nine of its stops.

## What did not work, or waits

- **Two prompt versions were taken back or refused.** A rewrite of the intake read worse than the version before it and was reverted whole. A schema change was refused by the provider's grammar limit, as described above.
- **A number in a prompt became the target.** "An early start is a first stop by 08:30" produced ten days that began at exactly 08:30, until the prompt named an aim and a limit.
- **Named places confirm 64% by name.** The share differs between the docs because the rounds differ: [grounding](grounding.md)'s 69% replays the matcher over the four rounds before the golden set took its twelve cities, 621 places; 64% is one round of the twelve on `day-v8`, and the [README's](../README.md#quality) 56% one run of them on `day-v10`, of 145 places; one round of twelve has a spread of its own. About half of the misses are walks named for a stretch of river or a street, which no search can find. Others are real places whose point the model set a few hundred metres off, or that the provider files as another kind.
- **The thresholds came from three hand-written days.** In the new cities, swap direction passes 4 of 12 days and walking radius 5. Neither threshold moves on one round.
- **Legs the clock cannot hold.** In Buenos Aires, 6.4 km on foot was given 30 minutes. A check for this, `leg-time`, now runs on every day: in the README's round, Sonnet's days pass it 10 times in 12.
- **Habits that belong to one day, not to one word.** Some days escape every accented letter, and the reader undoes that. Some days drop their accents entirely, and nothing undoes that.
- **What the checks cannot see.** Stockholm in December spent its six hours of daylight indoors while its summary claimed the opposite. A Sunday was offered a market that runs on Tuesdays and Saturdays. A person judges the voice against a written rubric. A model judge applies it in eval rounds, but missed the bar set before it ran (kappa 0.57 against the rubric's labels), so its numbers compare writers and never give a share of lines that pass ([the voice judge](harness.md#the-voice-judge)).
- **Haiku is not good enough to show the visitor.** Every day is also written by Haiku, at a twentieth of the price per token, about 24 times cheaper per day as measured, and logged as a pair with Sonnet's. Over three runs of the golden set and two more tries, at `high` effort and with its rules for versions said again, Haiku's days give the energy curve a version for 45 to 55% of its moves, against Sonnet's 71 to 76%, and they name venues as meals; the voice judge reads it behind on every role. Sonnet keeps writing the visitor's day, and Haiku stays its shadow ([round A](harness.md#round-a-haiku-against-sonnet)).

## What Lantern taught

- **A prompt is read whole.** The intake rewrite changed one instruction and one example together, and both moved answers no one targeted. One change per round costs more rounds and buys answers.
- **A rule without a check drifts.** The prompt asked for "time to get between them", and nothing measured it until a round in sprawling cities made it visible.
- **Stored output is free to score again.** Paid rounds go to new prompts. A new check runs over every recorded day the same afternoon.
- **What cannot be verified should not be named.** Every invented place was a venue, so Lantern stopped naming venues rather than trying to verify them better.
- **The provider's limits are a backstop, not a boundary.** The app's own reservation, held before every call, is what makes a public endpoint safe to share.
- **Fix a model's habit where every string passes.** Escaped letters are undone in the stream reader, once, instead of with a prompt line that might teach the habit.
